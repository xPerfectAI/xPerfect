01 / RUN XPERFECT

Start with the AI tools you already use.

A workspace keeps the files. A named AI Worker keeps its own work and native history. For the five professional starters in this guide, use Claude Code on your computer—their current supported Skill route.

PROFESSIONAL STARTERS

On your computer

macOS or Linux, Python 3.11+, uv and an installed Claude Code client. Your AI account connects through its own sign-in.

PACKAGE / ARM64 + AMD64

Docker alternative

The public Linux Arm64 and AMD64 packages start without building images. Use the worker routes it actually offers; host-only starters are not automatically available inside it.

SEPARATE SETUP

A team server

Hosted use needs trusted TLS, admitted users and configured storage. Windows host startup remains unqualified; hosted identity and storage need their own setup.

  1. Download and unzip xPerfect.

    Download the public source ↓. Open Terminal in that folder. Install Python 3.11+, uv and Claude Code.

  2. Start the app.
    ./xperfect start

    Choose an unlock password when asked, or save the generated one. Your saved work lives outside the source folder.

  3. Open and unlock it.

    Use the address printed in Terminal, normally http://127.0.0.1:8780. Enter the app password, then connect an AI account. A running page alone is not a connected AI.

Use the public Docker package instead

With Python 3.11+ and Docker running:

./xperfect start --docker

Use the printed app address and ui_password in its named private credentials file. Keep that file private; it also holds MCP credentials. Native worker choices, account setup and available abilities follow the package's actual configuration.

./xperfect start --docker --name xperfect-demo \
  --state-dir ~/xperfect-demo --ui-port 18780 --mcp-port 18767

Use those printed addresses for that instance. Never start two instances against the same state. Startup selects the matched linux/arm64 or linux/amd64 image pair for your Docker daemon.

Deploy on a server

Follow the hosted deployment guide. Opening a local port to the Internet is not a hosted setup; do not bypass its identity, TLS or filesystem requirements.

02 / CONNECT YOUR AI

Bring the account you already use.

  1. Open Connections.
  2. Choose your AI and account. For a container package, select Connect another account, choose Claude or Codex and follow its subscription sign-in. For the optional native host launcher, Use existing Claude sign-in can reuse Claude Code on that computer.
  3. Return after sign-in. Keep the same provider account selected for the expert. Do not copy provider credentials into a prompt.
  4. Wait for Ready.

    Ready means connected. Your first completed task proves it can do the work.

Account choice and safety

Use your intended account and exact model. The current package records gpt-6.1-sol for Codex and claude-opus-5-5 for Claude. An explicit choice takes precedence; no silent switch. A native host Codex worker without an explicit model uses its account default. Provider sign-in and genuine access confirmations remain yours. Host workers have your OS permissions; container workers use isolated workspaces. Your AI provider receives the task content needed for its work.

03 / CHOOSE WHO DOES THE JOB

A professional. A clear job. A usable result.

Start with a packaged profession, create your own worker, or continue an existing one. A saved expert setup creates a new worker; reusing a worker continues its own files and history.

  1. Open Run Project → Experts. Choose Finance Director. What's included shows its starting knowledge and abilities; the other four professions use the same ordinary worker pattern.
  2. Explain What's the Job? Add a required outcome if useful. For this example, use the supplied company brief, accounts, plan and job.
  3. Onboard the worker. In Required Knowledge → Background Context, add those files or choose your own saved Library material. Naming a file in a message does not upload it.
  4. Check who's doing it and where. Use a Ready Claude Code account on this host and a new My own workspace. Select Run Project; review included native abilities when asked.
  5. Open the actual report and editable calculations. Watch shows progress, guidance and file actions. Inspect the result, then reload the same worker rather than starting over.

Manual local connection and Docker differences

The app's generated command is the source of your actual state directory and endpoint. The host stdio route is ./xperfect mcp; local Docker uses its separately printed HTTP MCP address and private bearer key. Do not apply a host stdio recipe to a Docker instance. Follow the matching connection recipe.

What is retained when I copy or reuse?

An existing worker keeps its own native history and files. A new template worker is a separate identity. A same-owner copy may keep a Ready compatible selected account reference, but never copies provider credentials, browser sign-ins or native conversation history. An unavailable or mismatched account needs a new selection.

04 / BACKGROUND, KNOWLEDGE & ABILITIES

Get the worker fully onboarded.

  1. Give it the relevant material. Use Background Context for text/files when starting; an existing worker's Library → Files retains its ordinary workspace files.
  2. Reuse what already works. Choose exact saved knowledge, Skills or bundles from My Library. Added here shows the selected material for this worker.
  3. Review native abilities for this worker. A source link or saved Skill is not proof a plugin is installed. Use the native setup and actual-target review when asked; optional services retain their own accounts and permissions.
  4. Inspect the delivered work. Open/download the report and editable files. Use Keep for reuse on an exact captured result; use the separate current-file action when only present workspace bytes are available.

Company onboarding material stays in your private selection; it does not become part of a public starter. A Library bundle is reusable material, not another type of worker or a new orchestration framework.

05 / RUN IT LATER

Run a task. Or wake your app.

Run a task

Choose a saved AI workspace. Give it the next job, such as preparing Monday’s finance review. Its native account and permitted material stay with that worker.

Send to an app

Send a scheduled request to a connected app: a team reminder, an existing automation or your own assistant. This path needs a receiving app, not an AI account.

  1. Open Schedules → New schedule. Choose Run a task or Send to an app.
  2. Choose where it goes. Select your workspace or connected app. For a new app, use Connect an app, give it a name and enter its receiving address. Follow the receiver’s signing and payload setup.
  3. Write the request and choose when. Set a one-time run or repeat, then check the time zone and create the schedule.
  4. Check the first delivery. Use Run now and open More → View history. Check the receiver for its completed work.
Received by the app means the receiver acknowledged the request. It does not mean the app finished its job. Keep xPerfect running; an unavailable receiver or busy AI account has its own recovery state.

06 / REUSE & SHARE THE INTERFACE

One expert. More than one way in.

In the app

Open Workspaces, find your active worker, and open it. Use Steer for the next request. Reopen Files to check the saved result. If it is Closed, use Duplicate for fresh work.

Use More → Duplicate to copy ordinary files and installed native skills. The copy keeps the same ready personal AI account; credentials, private harness sessions and run history are not copied. If that account is no longer ready, choose an account again.

In Codex or Claude

“Find my Finance Director in xPerfect. Ask the same worker to explain this revised cash assumption. Preserve its original report and make the change clear.”

The client discovers the actual tools. Save the worker/workspace ID rather than inventing a new endpoint for each expert.

Manage experts and workspaces
  1. Save and improve an expert. In Workspaces → More → Save as expert, keep a worker’s setup. Open Run Project → My experts → Manage to Edit a new version, Copy a separate expert, or inspect Versions. Existing workers keep their original setup.
  2. Put an expert aside. Choose Archive or confirm Remove. Use the Archived or Removed filter and choose Restore to make it available again.
  3. Clear a workspace card from your list. Choose Workspaces → More → Remove and read the confirmation. Its current and scheduled work stops, but its files, results and history stay saved. In Removed, Restore brings the same card back Closed; it does not restart work. Duplicate creates a fresh worker.

Removed one-off workspaces are kept too. Removal is recoverable; it does not permanently erase files or free that saved storage. Close stops compute without removing the card.

Optional skill: “xPerfect this…”

The repository already includes skills/connect-glasshive/SKILL.md. Its name stays for compatibility. It is guidance for the native client, not another service.

Install this existing skill in your controlling client’s normal skill folder: .agents/skills/connect-glasshive/SKILL.md for Codex or .claude/skills/connect-glasshive/SKILL.md for Claude Code. Use the published skill. Connect MCP once using the appropriate recipe, then ask it to use the selected professional or existing worker for your real job. The native client chooses the tools; no extra service is needed.

Build it into a product: MCP / API

Use the existing control plane: create a saved expert with workspace_launch and favorite=true, then find, message, copy, schedule or retrieve its files. Put ordinary files and native skill folders inside its workspace. Local Docker MCP uses the private bearer key; host stdio uses the current OS identity. Hosted clients use the service’s registered human sign-in.

workspace_list workspace_launch workspace_schedule workspace_wait worker_message workspace_status workspace_artifacts workspace_duplicate

The direct local API is separate from the UI: by default 127.0.0.1:8766. Use its private API token in the Authorization header, never a URL. Docker packages keep that runtime API private; use their exposed authenticated MCP.

A saved expert launch (favorite=true) works from a plain connected MCP client. Only a fresh one-off launch without favorite requires an integrated host’s trusted source identity. Use reuse_existing_workspace=true for the same expert by exact name. See the API and client examples.

WHEN SOMETHING STOPS

Follow the cause, not a retry loop.

You see Do this
No ready account Connect the account for the selected worker. Wait for Ready, then run one small task.
Queued / account busy Check the active workspace. Let it finish; do not launch copies to force progress.
Approval required Read the exact provider, client or sharing request. Approve only the intended access as its owner. Ordinary use of an already authorized ready account does not need a new routine account grant; never switch identities to bypass a refusal.
Missing result Check Watch and Files. A completed model answer and a downloadable artifact are different evidence.
Docker network error Read Docker’s reported cause. For exhausted address pools, use unused network ranges as described in the package guide. Do not prune personal volumes or repeat an unchanged failed launch.
App restarted Use the same state directory. Reopen the workspace and verify files before resubmitting work.
Restart the same Docker package

After Docker or the computer restarts, start your saved package:

docker start xperfect-local-runtime xperfect-local-ui xperfect-local-mcp

Use your package name if you changed it. Files, account state and the unlock password stay in its existing volumes. Check Watch and Files before resubmitting uncertain work. For a supported update or restore, follow the deployment guide; never replace saved state as a retry.
